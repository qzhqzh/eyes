# 产品愿景与边界

## 一句话定位

Eyes 是面向个人机房、小团队和边缘设备的轻量资源网络，让 AI Agent 能以统一、安全、可审计的方式发现并使用分散在不同机器上的资源。

## 从监控工具到资源网络

当前 Eyes 解决“这台机器上的服务是否健康”。目标形态需要继续回答四个问题：

1. 网络中有哪些节点，它们在哪里、承担什么角色？
2. 每个节点具备哪些能力，当前有哪些可用资源？
3. 某个 AI Agent 的任务最适合在哪个节点执行？
4. 如何预留、执行、回收资源，并把状态、日志和结果安全返回？

因此完整闭环是：

```text
Discover -> Describe -> Match -> Reserve -> Execute -> Observe -> Release
```

监控是其中的 `Discover` 和 `Observe`，资源利用需要补齐其余环节。

## 核心用户与场景

### 资源所有者

- 将家中、办公室、云主机、NAS 或 GPU 工作站接入同一 Hub。
- 声明机器的定位，例如 `role=gpu-worker`、`site=home`、`zone=study`。
- 设置哪些资源可供调度、保留多少给本机、允许运行哪些工作负载。
- 查看资源利用率、节点健康、任务历史和安全审计。

### AI Agent

- 查询“哪里有空闲 GPU、足够内存、指定模型缓存或某项服务”。
- 提交结构化的批处理、推理、转码、构建或数据处理任务。
- 获取任务状态、日志摘要和输出制品。
- 不需要知道节点 IP、登录凭据、Docker Socket 或 SSH 密钥。

### 节点维护者

- 一条安装命令让 Agent 作为服务启动。
- 节点在 NAT 后也能主动连接 Hub。
- Hub 不可用时本机业务不受影响，Agent 能缓存必要状态并自动重连。

## 产品原则

### 资源目录与执行解耦

“节点能做什么”和“节点现在执行什么”是两个独立模型。Agent 可以只上报资源而不允许执行，也可以只暴露一个已经存在的推理服务。

### 声明式请求，不暴露机器

AI Agent 描述所需能力和资源，由 Hub 选择节点。资源使用权限默认不包含宿主机管理权限；具有明确维护授权的操作者或自动化 Agent 可以申请短期 ShellSession 直接维护节点。

### 租约优先于瞬时空闲率

CPU 使用率低不代表资源已被可靠分配。调度以请求、预留和租约为准，实时指标只作为评分和保护信号。

### 节点拥有最终准入权

Hub 可以做全局调度，但节点必须在执行前再次验证资源、策略、镜像和租约。Hub 的旧状态不能强迫节点超额执行。

### 渐进增强

几十台以内先保持部署简单；当真实规模和可靠性需求出现后，再引入 PostgreSQL、时序数据库、消息总线或多 Hub。

## 非目标

- 不替代专业集群编排器；已有 Kubernetes、Nomad 或 Ray 时，Eyes 应作为统一资源入口和适配层。
- 不自行实现 Mesh VPN；读取并整合 WireGuard、Tailscale 或 Headscale 状态。
- 不承诺在不受信任节点上保护恶意资源所有者的数据；节点信任域必须显式建模。
- 不把无条件、长期凭据的远程 shell 作为默认资源使用方式；受策略控制的节点维护 shell 属于正式能力。

## 术语

- **Eyes Node Agent**：安装在机器上的系统守护进程。
- **Consumer Agent**：通过 Eyes 使用资源的 AI Agent。
- **Capability**：节点能提供的功能，例如 Docker 执行、NVIDIA GPU、HTTP 探测或某个推理服务。
- **Resource**：可计量或独占使用的容量，例如 CPU、内存、GPU、磁盘空间和带宽。
- **Workload**：Consumer Agent 提交的结构化执行请求。
- **ResourceClaim**：工作负载对资源的声明。
- **Lease**：Hub 与节点共同确认、带期限和 fencing token 的资源占用权。
- **Artifact**：任务输出的文件、对象、模型或结构化结果。
- **ShellSession**：绑定操作者、目标节点、权限范围、期限和审计策略的临时维护会话。
